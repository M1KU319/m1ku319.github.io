Persistent Data Structure - Segment Tree

Persistent Data Structure - Segment Tree

A persistent data structure is a data structure that always preserves the previous version of itself when it is modified. Such data structures are effectively immutable, as their operations do not update the structure in place, but instead always yield a new updated structure.

You should be familiar with basic segment trees before reading this post.

Problem Statement

Persistent Segment Tree

You need to maintain an array aa with a length of NN, supporting the following two operations:

  1. Modify the value at a certain position in some historical version
  2. Query the value at a certain position in some historical version

In addition, each operation creates a new version. The version number is the index of the current operation, starting from 1, while version 0 represents the initial state of the array.

For operation 2, the newly created version is completely identical to the version being queried, with no modifications made. In other words, the version generated by a query operation is simply a copy of the version that was queried.

Input Format

The first line contains two positive integers NN and MM, representing the length of the array and the number of operations, respectively.

The second line contains NN integers, where the ii-th integer is aia_i.

The next MM lines each contain either 3 or 4 integers, representing one of the following two operations. Suppose the current operation is the ii-th operation:

  1. For operation 1, the format is v 1 p c, meaning that based on version vv, set apa_p to cc.
  2. For operation 2, the format is v 2 p, meaning that we query the value of apa_p in version vv. Note that this operation also creates a new version that is identical to version vv.
  • 1≤N,M≤1061 \le N, M \le 10^6
  • 1≤p≤n1 \le p \le n
  • −109≤ai,c≤109-10^9 \le a_i, c \le 10^9

Copy the path

It is not hard to see that the limit is not the time complexity, but the space complexity. If we build a separate segment tree for every version, we will definitely exceed the memory limit.

If we change the value of a leaf node, only the node on the path from the root to that leaf node would change, so that we only want to copy the path instead of creating a new tree. This is the idea behind a persistent segment tree.

You can find that a new root corresponds to a new version, and different versions share some nodes. Because of that, we cannot use (idx * 2) and (idx * 2 + 1) to calculate the left son and right son.

This only copies the three integers stored in the current node. It does not recursively copy the entire subtree. At this point, the new node and the old node temporarily point to the same left and right children.

Next, we recurse only into the side that contains q - the target path that we want to copy, and connect the returned new child index to current. The child index on the other side remains unchanged, which allows the two versions to share unchanged subtrees.

Throughout the recursion, we maintain the two invariants:

  • the old node is never modified
  • in the new subtree, only the value at position q is changed.

At the leaf node, we directly assign the new value. As the recursion returns, we reconnect the copied nodes along the path, eventually obtaining the root of the new version.

It’s not enough to copy only the leaf node, since the leaf’s parent must point to the new leaf, and the parent’s parent must also point to the new child. Therefore, the entire path from the leaf up to the root must be copied.

Query

Just head out from the root node, choose the left subtree or the right subtree according to the query position, and return the value when you reach the target leaf node.

Attention: a query also creates a new version. Since no values change, the new version can share the entire tree.

Space Complexity

The initial segment tree has nn leaf nodes. Since every internal node has exactly two children, the tree contains a total of 2n−12n-1 nodes.

Suppose there are uu update operations. Each update copies at most ⌈log⁡2n⌉+1\lceil \log_2 n\rceil+1 nodes, including the root and the leaf. Therefore, an upper bound on the total number of nodes is

(2n−1)+u(⌈log⁡2n⌉+1). (2n-1)+u\bigl(\lceil\log_2 n\rceil+1\bigr).

For n,m≤106n,m\le 10^6, each update creates at most 21 new nodes, so the total number of nodes is less than 2.3×1072.3\times10^7. In the implementation below, we reserve MAXN * 23 nodes for the node pool.

The node indices, version indices, and point values in the range [−109,109][-10^9,10^9] all fit within a 32-bit int. In a typical environment where an int takes 4 bytes and each node takes 12 bytes, the node pool uses about 263 MiB. Together with the base and root arrays, the three arrays use about 271 MiB in total. Since there are no range-sum queries in this problem, there is no need to use long long for every field.

More precisely, the complexities are:

  • Building the initial tree: O(n)O(n).
  • Each update or query: O(1+log⁡n)O(1+\log n).
  • Total space: O(n+m+u(1+log⁡n))O\bigl(n+m+u(1+\log n)\bigr), where the root array itself takes O(m)O(m) space.

In most cases, we simply write the complexity of each operation as O(log⁡n)O(\log n), and the total space complexity as O(n+mlog⁡n)O(n+m\log n).
